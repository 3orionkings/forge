# Liveness and recovery observation

Liveness measures **objective or artifact progress**, not chatter. Narration,
heartbeats, repeated status text, and a model saying it is busy are not completion or
progress evidence.

Use the typed [`forge_status`](bridge-tools.md) for a current snapshot and the
documented bounded `forge_wait` for a revision change; both are defined in
[bridge-tools.md](bridge-tools.md). Every wait returns within the
runtime's 30-second cap. Longer monitoring is a sequence of bounded observations with
fresh user-facing updates, never one hidden blocking call.

## Runtime instruments

- [`scripts/forge-liveness.sh`](../../../scripts/forge-liveness.sh) is a read-only,
  provider-neutral classifier over exact durable job/attempt/revision evidence.
- [`scripts/recovery-watchdog.sh`](../../../scripts/recovery-watchdog.sh) is retained
  as unfinished historical recovery machinery and is not an enabled release path.

Both instruments are local and provider-free. Liveness **never signals or kills** a
process. Cancellation occurs **only through `forge_cancel`** as documented in
[bridge-tools.md](bridge-tools.md).

## Status polling

Persist the explicit job ID and latest revision. A status response may include the
current attempt/session, requested and observed model, accounting, progress summary,
and pause/failure classification. Do not select a job from a "latest" convention.

Use a bounded wait when the state is expected to change:

1. pass the exact job and observed revision;
2. choose a timeout no greater than 30,000 ms;
3. inspect `wait_timed_out`, new revision, and state;
4. report meaningful state or artifact change;
5. repeat only while the task remains authorized and within owner bounds.

A timed-out wait is an observation, not failure. Fast repeated polling that yields no
new objective evidence is chatter generated by the orchestrator.

## Read-only liveness classifier

The liveness script requires exactly absolute state path, explicit job ID, explicit
attempt ID, and exact revision. It reads private schema-v12 SQLite state without
initializing or migrating it and returns bounded JSON.

Classification precedence is:

1. validated terminal receipt: `DONE`;
2. validated provider or policy pause: the matching pause status;
3. other non-running or unobservable state: `UNAVAILABLE`/`INVALID`;
4. definitively stopped recorded worker/provider identity: `STOPPED`;
5. repeated stderr signature newer than objective progress: `STALLED`;
6. objective/artifact progress younger than 1,200 seconds: `ALIVE`;
7. otherwise, positive CPU delta from exact recorded processes: `ALIVE`;
8. no CPU delta and no objective progress for at least 1,200 seconds: `STALLED`.

An ALIVE receipt can defer a stall check but cannot advance the objective, clear a
failure, prove an artifact, satisfy proof, or authorize integration.

## Native-lane liveness

Use [`scripts/forge-native-lane.py`](../../../scripts/forge-native-lane.py) `list`
to observe the shared ledger and its `heartbeat` operation only with the pinned
owner-private receipt. Heartbeat preserves the same lease and does not prove
objective progress, completion, or descendant quiescence. A stale native lease
remains counted until authenticated release or explicit manual owner action;
liveness never frees it.
Invoke `release` only after the native agent and all descendants are quiescent. A
missing receipt is an owner-action gate, not permission to forge a release or spawn
an overlapping replacement.

## Recovery is disabled

Automated recovery and recovery-watchdog mutation are disabled in this release.
Continue to use exact status and the read-only liveness classifier for evidence, but
do not initialize or update recovery state, transfer a role, or launch a replacement.
Preserve the worktree and receipts unchanged and request a manual owner handoff.

## Pauses are never handoffs

`paused_provider` and `paused_policy` are **never handoff-ready**. The executable
states are `PAUSED_PROVIDER_ACCESS` and `PAUSED_POLICY`; both escalate for owner action
before repeat-failure or stall handoff logic. Preserve their receipt and ask. Do not
assign the same frozen unit to another model while the original job could still
resume or write.

## STALLED or STOPPED response

1. Re-read typed status and exact liveness evidence to rule out stale revision.
2. Preserve worktree, report paths, logs, unit contract, job/attempt, and receipt.
3. Report the exact evidence and request a manual owner handoff; do not mutate the
   recovery ledger or start a recovery job.
4. If cancellation of a non-recovery job is needed, the Codex driver requests it through the typed bridge
   and waits for terminal quiescence evidence.

Never race a still-live writer with a recovery lane. Never use a liveness result as a
substitute for cancellation, admission, provider approval, proof, cross-model review,
or Codex verification.

## DONE response

DONE means the terminal receipt is valid, not that the change may be integrated.
Retrieve the result and apply the active profile:

- Sprint: admitted-path/overlap/safety checks plus executor proof receipt, then
  immediate serial integration and eventual sprint-end gate.
- Assured: genuine cross-model receipt, Codex complete-diff review and proof rerun,
  serial integration, then the integrated gate.

Only Codex applies the integration or commit decision.
